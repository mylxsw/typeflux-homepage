最近，我经历了一次非常惨痛的 AI 开发翻车事故。

整整跑了两天、拆分了近 20 个子任务、烧掉了 1023.32 美元的 Token 成本，最后面对跑出来的代码，我只能无奈地敲下 `git reset --hard`，把所有改动全量回滚。

> 27 亿 Token，主要是 Claude Opus 5.5、GPT-6-Astra、GPT-6.1-SOL 模型，我在 ChatGPT 和 Claude 都订阅的 Pro/Max 会员，所以实际成本没这么高😄。

这次惨痛教训让我彻底清醒：**哪怕到了 AI Agent 时代，传统的软件工程重构法则依然没有过时。盲目迷信 AI 的全自主大重构，只会被现实狠狠上一课。**

今天把这次踩坑复盘写下来，希望能给正在尝试用 AI 辅助重构或全自动开发的朋友提个醒。

## 01. 问题的起因：多 Agent 并行一时爽，UI 碎片化火葬场

最近我一直在升级自己的项目 **Typeflux**。它的定位正在从单纯的语音输入法，逐步演进为“启动器 + 语音输入法 + AI Agent”的综合形态。

![image.png](https://r.wy.is/bilingual-reader/production/d96ebf2a-4075-47bc-8ee0-7fd91a34621d/materials/6c5f2f99-73c8-406d-8fe2-2494b57a2ab2/08b7f216-a31f-4045-af74-506dc6cdb421 "image.png")

为了提升开发效率，我安排了多个 Agent 同时去实现不同的新功能模块。经过多轮迭代后，功能确实丰富了，但很快就暴露出一个极度让人抓狂的问题——**整个应用的 UI 组件彻底碎片化了。**

* 页面标题样式混乱：在这个设置页里是一种字号和间距，到了另一个设置页里又是另一种风格；
* 核心交互组件形态各异：以搜索框为例，有的地方是输入后动态展开的交互，有的地方是固定圆角展开，还有的地方干脆是方角形态。

各个 Agent 在实现功能时“各显神通”，缺乏全局约束，导致整体 UI 极不协调。

## 02. 我的“完美设想”：来一场系统级的全量自动重构

面对这堆混乱的界面，我萌生了一个大胆的想法：**让 AI Agent 帮我做一次系统级的全局 UI 大重构。**

为了防止它乱来，我还特意制定了一套看似缜密的“重构 SOP”：

1. **确立设计规范**：先让 Agent 产出一份全局 UI 设计规范，我审核满意后才准进入下一步；
2. **抽取统一组件库**：将散落各处的元素标准化，抽象成可复用的 Component 组件库；
3. **逐页迁移替换**：最后遍历每一个功能页面，全量替换为刚构建好的新组件。

不仅如此，任务架构也拉得非常饱满：

* **任务编排**：整个大任务拆分成了接近 20 个子任务；
* **模型分工**：主控 Agent 采用 Claude Opus 5.5 负责全局调度与规划，执行子任务的 Agent 则分别使用 GPT 6.1 SOL 和 GPT 6 Astra；
* **质量保障**：每次修改代码都必须同步运行单元测试，绿灯通过后才能进入下一个节点。

布置完这一切，我觉得链路清晰、保障到位，便放心地让任务在后台跑了起来。

## 03. 翻车实况：两天漫长等待，换来一堆“合法垃圾”

因为每个子任务都要边改代码边跑单测验证，整个进度非常缓慢。

我足足等了近两天。直到整个任务链执行完毕，满心期待地打开界面一看，我整个人愣住了：**结果差劲得完全超出了预期。**

虽然所有的单元测试全部绿灯通过，代码逻辑没有任何报错，但在视觉和用户体验层面，整个界面几乎到了“无法直视”的地步：

* 布局比例严重失调；
* 很多页面为了强行套用抽离出来的组件，破坏了原本合理的交互结构；
* 视觉统一性不仅没有改善，反而多了一层“僵硬拼凑”的怪异感。

苦等两天、烧了 1000 美元 Token，最终收获的却是一套完全无法投入生产的代码。没有别的选择，我只能把这两天由 AI 产出的所有改动全部回滚，重新回到重构前的起点。

## 04. 深度复盘：我学到了哪三条血泪教训？

看着空荡荡的 Git Log，我认真复盘了这次之所以“大败退”的核心原因：

### 1. 单元测试测得出逻辑对错，测不出视觉协调

这是最大的认知盲区。子 Agent 在重构页面时，关注的核心是“功能有没有跑通”、“测试用例有没有报错”。然而，**UI 和交互的美感、协调感、层级节奏，是单测完全无法量化的。** 最终 AI 给出的结果是：代码逻辑全对，但界面视觉一塌糊涂。

### 2. 软件工程没有银弹，必须坚守经典重构方法论

在 AI 时代之前，软件工程就反复强调：**不要搞“大爆炸式（Big Bang）”的全量重构**，而要遵循“小步快跑、逐步演进”。这次我贪图省事，试图让 AI 一步到位把全系统几十个页面全量翻新，违背了基本的工程规律，失败是必然的。

### 3. 反馈闭环过长，失控的 Agent 会在错误基线上狂奔

两天的重构周期里，我把控制权全权交给了 Agent，缺乏中间的“人机校验（Human-in-the-loop）”。一旦中间某个组件设计或页面迁移出现了审美与交互上的偏差，后续近十个子任务就会基于这个错误基线继续叠加错误。最后哪怕察觉出问题，修正成本也已经高到无法承受。

## 05. 接下来怎么做：回归小步迭代与“人在回路”

吃一堑，长一智。接下来对 Typeflux 的 UI 统一，我将彻底放弃“全自动全量重构”的幻想，回归到扎实的传统工程模式中：

1. **细化颗粒度，分模块单点突破**：不再做全量任务包，一次只重构一个独立模块或单一交互组件；
2. **重构一步，人工验证一步**：每完成一个组件的抽象与替换，立即在真实环境中运行预览，人工确认视觉与交互体验无误后，再打 Commit 固化；
3. **让人做审美裁判，让 AI 做编码打手**：AI 依然是极其强大的重构辅助工具，但审美决策与交互把关的权利，必须牢牢握在开发者自己手里。

从小处着手，一步一个脚印，才能最终改出满意的系统。
